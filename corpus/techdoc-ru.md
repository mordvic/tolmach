## Синхронизация сессии

Сервер профилей считается источником истины для состояния сессии. Клиент не должен самостоятельно продлевать срок жизни токена — он обязан дождаться ответа от `/session/sync` и применить полученное состояние целиком. Заголовок `Authorization` обновляется только после успешного ответа сервера.

```typescript
const state = await syncSession({ signal: controller.signal });
if (state.status === "revoked") {
  await hardLogout({ reason: "server-revoked" });
}
```

Если запрос завершился таймаутом, повторите его с экспоненциальной задержкой, но не более трёх раз. Полную спецификацию протокола см. на странице https://example.org/docs/session-sync, раздел «Session Sync».

> **Важно:** повторные попытки не должны блокировать основной поток интерфейса.

Подробности — в журнале изменений релиза 19072.

## Отзыв токена

Токен считается отозванным сразу после того, как сервер получил запрос на выход хотя бы с одного устройства. Клиенту нельзя доверять локальной копии токена дольше, чем позволяет `/session/sync`: даже если токен выглядит действительным, сервер может отклонить его на следующем же запросе. Приложение обязано обрабатывать отозванный токен так же, как истёкший, и не пытаться продлить его самостоятельно.

Повторный вход после отзыва токена требует полного цикла аутентификации — сохранённый токен для этого не годится. Разработчики, которые кешируют токен в памяти дольше одного запроса, регулярно сталкиваются с этой ошибкой: интерфейс продолжает работать с отозванным токеном, пока пользователь не обновит страницу вручную.

## Логирование отказов сервера

Каждый отказ сервера при синхронизации сессии должен попадать в журнал с указанием причины и идентификатора запроса. Без идентификатора запроса невозможно сопоставить отказ клиента с записью на сервере, а без понятной причины отказа непонятно, был ли токен отозван намеренно или сервер столкнулся с внутренней ошибкой.

Команда поддержки регулярно жалуется на отказы без объяснения причины — такие записи в журнале почти бесполезны при разборе инцидента. Если сервер вернул отказ, клиент обязан записать в журнал полный текст ответа сервера, а не только код состояния.

> **Важно:** журнал отказов не должен содержать сам токен, только его идентификатор.

Отказы сервера стоит группировать по идентификатору клиента, а не только по времени: один и тот же клиент, теряющий токен раз за разом, обычно указывает на ошибку в самом клиенте, а не на проблему сервера. Такую закономерность легко упустить, если смотреть на журнал отказов построчно, а не по идентификатору запроса.
